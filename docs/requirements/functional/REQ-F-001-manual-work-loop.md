## 问题与使用场景

用户有一个需要持续推进的目标，希望将它组织为模块和事情，再记录可以执行的事件。完成一次行动后，需要保留行动记录，并能区分尚待执行和已经完成的事件。

价值：先让用户能完整记录、找到和完成自己的工作，为后续拆分、关联、优先级和智能辅助提供明确的业务对象。

## 范围与事实边界

产品架构已明确四类对象以及事件可完成的原则。本切片拟提供手动创建、查看、修改名称及说明、完成事件、再次查看保存结果的闭环。

以下首片范围随需求稿于 2026-11-12 获用户认可；交互呈现仍待原型确认：

- 首片仅考虑个人使用，不包含共享和指派。
- 模块必须属于一个目标，事情必须属于一个模块，事件必须属于一件事情；首片不提供独立事件或跨层归属。
- 事情与事件均有“未开始、进行中、已完成、已取消”四种状态，由用户手动调整。两者均记录计划开始时间、计划结束时间和责任人。来源：2026-11-12 用户原型评审补充；“事情和事情”按上下文理解为“事情和事件”。
- 完成事件只改变该事件，不自动完成事情、模块或目标，不计算百分比进度。
- 首片不提供移动归属、删除或归档，避免提前引入生命周期和引用处理规则。

责任人先采用手动姓名录入，不接入通讯录或自动指派。原型设计暂允许计划时间和责任人留空，分别显示“未设置”和“未指定”；不虚构日期或人员。计划结束不得早于开始。撤销完成在原型中恢复未开始；已取消事件通过编辑恢复。上述交互细节随原型评审确认。

## 用户操作

1. 用户明确提交名称及可选说明，创建目标。
2. 在选中的目标下创建模块，在选中的模块下创建事情，在选中的事情下创建事件。
3. 浏览层级并选择事情，查看其事件及状态；能回溯事件所属目标、模块和事情。
4. 修改对象名称或说明，提交后展示实际保存结果。
5. 手动完成事件，或显式撤销完成；重新打开后仍可看到保存的内容和状态。

## 异常与边界

- 名称为空或仅为空白时拒绝保存并提示原因，保留已填写内容。
- 创建子项前必须检查父项存在且在当前用户可操作范围内；无权或父项失效时拒绝，不自动改挂到其他对象。
- 所有修改检查对象范围及当前状态；过期状态造成冲突时提示刷新，不静默覆盖。
- 连续提交同一次创建操作不得产生重复对象；同名不作为重复操作的唯一判断依据。
- 重复完成已完成事件不得产生第二次状态变化。
- 保存失败或结果无法确认时，不显示成功，不自动重试写操作；保留输入并允许用户核对结果。
- 每次写入完成后读取实际结果；只有核对成功才展示保存成功。

## 验收条件

| 编号 | 可观察结果 |
|---|---|
| AC-01 | 用户可通过手动操作建立完整的目标、模块、事情、事件链，并查看准确归属。 |
| AC-02 | 修改名称及说明后，重新打开仍能看到实际保存内容。 |
| AC-03 | 完成事件后，重新打开仍为已完成；其他对象状态不受影响。 |
| AC-04 | 显式撤销完成后恢复未开始，且结果可重新读取。 |
| AC-05 | 空名称、父项不存在、越权和状态冲突均被拒绝，未产生部分写入。 |
| AC-06 | 同一次创建的连续提交仅产生一个对象；重复完成不产生额外状态变化。 |
| AC-07 | 保存失败或读回失败时不显示成功，用户输入仍保留。 |
| AC-08 | 无数据时提供清晰的首次创建入口；未选择父项时不允许误建子项。 |

| AC-09 | 事情与事件均可查看、编辑计划开始时间、计划结束时间、责任人和四种状态，保存后可重新读取。 |
| AC-10 | 计划结束早于开始时拒绝保存并保留输入；取消事件不计入待完成数量。 |

## 日期粒度修订（2026-11-13）

来源：用户明确要求计划开始和结束只到天。事情与事件统一输入、展示 YYYY-MM-DD，可为空，允许同一天；结束日期不得早于开始日期。新写入不接受时分。历史本地日期时间读取时仅返回原日历日期，不做时区换算，不批量改写既有数据；用户再次保存时按日期存储。此规则替代此前时分粒度描述。
